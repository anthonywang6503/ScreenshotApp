# ADR-0012：畫布縮放模型——100% = 1 圖片像素 = 1 實體像素

- **狀態**：Accepted
- **日期**：2026-10-18

## 背景

編輯器需支援符合視窗、100% 與 25%～400% 的縮放及平移；縮放、平移或調整視窗不得改變輸出。開發機與多數使用者的螢幕縮放不是 100%（例如 175%），若以 WPF 的 DIP 定義縮放，「100%」在高 DPI 螢幕上會把每個圖片像素放大成 1.75 個實體像素，截圖看起來模糊、也無法逐像素檢查。座標換算必須集中於 `CoordinateMapper`，控制點在各縮放下需維持固定的螢幕尺寸，命中判定的容差也應以螢幕像素定義。

## 決策

1. **縮放比例 zoom 定義為「每個圖片像素占幾個實體像素」**。WPF 縮放容器的比例（每圖片像素幾 DIP）為 `zoom / dpiScale`，由 `CoordinateMapper` 計算；視窗移到不同 DPI 的顯示器時重新計算。
2. **畫布結構**：`ScrollViewer` → 內容根（至少與可視區域同大，接收滑鼠輸入）→ 置中的縮放容器（`LayoutTransform` 為上述比例，內含底圖、標註層與文字輸入層，區域單位即圖片像素）。控制點與選取外框所在的控制點層**位於縮放容器之外**，以 DIP 繪製，在任何縮放下都是固定的螢幕尺寸。
3. **Image ↔ ViewDip 換算只在 `CoordinateMapper`**：以「比例 + 圖片原點在控制點層中的位置」描述一次轉換；原點由 WPF 版面取得，換算公式（圖片 → DIP、DIP → 圖片、螢幕長度 → 圖片長度、浮點 → 整數像素）只寫在 mapper。滑鼠輸入、控制點繪製、命中容差與以游標為中心縮放的捲動位移都經由這些函式。浮點換整數像素採無條件捨去並容許極小的浮點誤差，使 100% 時游標所在的實體像素精確對應同一個圖片像素。
4. **縮放操作**：預設階段 25%、33%、50%、67%、100%、150%、200%、300%、400%；Ctrl+滾輪以游標下的圖片位置為中心切換階段，縮放後該位置仍在游標下；「符合視窗」取「放得下且不超過 100%」的最大縮放（超大圖片可低於 25%），在符合視窗模式下調整視窗會重新計算。空白鍵按住或滑鼠中鍵拖曳可平移。
5. **取樣方式**：縮放 ≥ 100% 時底圖以最近鄰取樣，可清楚看到每個像素；低於 100% 時使用高品質縮小。
6. **裁切的顯示**：一般狀態只顯示裁切範圍（縮放容器剪裁並平移），即所見即所得；裁切工具啟用時顯示整張原圖並將裁切外暗化，方便重新放大裁切範圍。
7. **100% 是否精確落在實體像素格線，以實機比對裁決**：版面取整與 `LayoutTransform` 的組合在非整數 DPI 下的行為不靠推論，實機煙霧驗證在 100% 時把畫布與已知圖樣逐像素比對；若有偏移再調整對齊方式。

## 考慮過的替代方案

- **以 DIP 定義縮放（100% = 1 DIP）**：高 DPI 螢幕上 100% 不是原尺寸，與「尺寸以圖片像素為準」及逐像素檢查的需求衝突。
- **自繪畫布並自行處理平移與捲軸**：可完全掌握轉換，但需自行實作捲軸、鍵盤捲動與版面置中，程式量與風險較高；文字輸入框也需手動套用同樣的轉換。
- **以 `GetPosition(標註層)` 直接取得圖片座標**：輸入正確，但控制點層、命中容差與縮放捲動仍需要同一組換算，換算分散後無法以自動化測試驗證。
- **`RenderTransform` 縮放**：不影響版面尺寸，`ScrollViewer` 無法得知放大後的範圍。

## 影響

- 縮放與平移的換算可單元測試（往返誤差、捲動位移使游標下的點不動、取整規則）；畫面上的實際對齊另以實機驗證。
- 文字輸入框位於縮放容器內，字級即圖片像素，輸入時看到的大小與輸出一致。
- 縮放只改變顯示，不修改文件；輸出由 `ImageRenderer` 依文件產生，與畫布縮放無關。
