# ADR-0014：剪貼簿格式策略——DIB 與 PNG 兩種格式，沿用執行階段的重試

- **狀態**：Accepted
- **日期**：2026-10-18

## 背景

按鈕或 `Ctrl+C` 要把合成後的圖片放入 Windows 剪貼簿，成功後顯示輕量提示並保留編輯器與文件。剪貼簿被其他程式占用時，應執行有限次短暫重試；仍失敗時顯示錯誤並保留圖片，不得假裝成功。複製與 PNG 存檔得到的可視像素必須一致，並以 PowerPoint 實際貼上驗證、確認 Word 與 Teams 可以接收。PNG 與剪貼簿共用唯一的圖片合成器，耗時的圖片編碼不應長時間阻塞 UI 執行緒。

Phase 2、3 的做法是只放一份 24 位元 DIB：`Clipboard.SetImage` 每次呼叫都會在本處理程序留下一個 GDI 物件，因此改以 DIB 位元組提供圖片。.NET 10 的 WPF `Clipboard.SetDataObject` 本身已有重試：`OleSetClipboard` 與 `OleFlushClipboard` 失敗時各自最多重試 10 次、每次間隔 100 ms，之後才拋出例外。

## 決策

1. **兩種格式，同一張合成結果**：
   - `DeviceIndependentBitmap`：24 位元、由下而上、96 DPI。只認得點陣圖的程式使用它；需要 `CF_BITMAP` 的程式由 Windows 從 DIB 自動轉換。
   - `PNG`：以 `PngBitmapEncoder` 編碼的同一張圖片，與另存 PNG 的編碼方式相同。支援 PNG 的程式（Office、瀏覽器與以瀏覽器技術製作的應用程式）直接取得與 PNG 檔相同的像素，不經接收端轉換。
   - 不放 32 位元 DIB 或 `CF_DIBV5`：接收端對其中 alpha 的解讀不一致。不使用 `Clipboard.SetImage`（GDI 物件洩漏）。
2. **執行緒**：在 UI 執行緒合成（`RenderTargetBitmap`，結果凍結）；DIB 與 PNG 位元組在背景執行緒由凍結的圖片產生；回到 UI 執行緒後以 `Clipboard.SetDataObject(data, copy: true)` 放入剪貼簿，程式結束後內容仍保留。
3. **重試**：以 .NET 執行階段內建的重試作為「有限次短暫重試」，不另加外層重試。外層再重試 5 次會與內建的 10 次相乘，剪貼簿被占用時 UI 執行緒可能阻塞約 10 秒。
4. **失敗**：回傳 HRESULT。`CLIPBRD_E_CANT_OPEN`（`0x800401D0`）顯示「剪貼簿正被其他程式使用」，其他錯誤顯示錯誤碼。文件與編輯狀態完全不變，也不標記為已匯出；只有成功時才在狀態列提示並記錄匯出時的文件版本。
5. **不重疊**：複製或儲存進行中，兩個命令都停用，不排隊。
6. **可測試性**：實際寫入剪貼簿的步驟以委派注入。單元測試不寫入使用者的剪貼簿：以 COM `IDataObject.GetData`（`OleFlushClipboard` 取得資料的同一種呼叫）確認兩種格式都能轉成 `HGLOBAL`、解碼後像素相同；以拋出例外的替身驗證失敗路徑與訊息。實際剪貼簿與占用情境由煙霧腳本驗證。

## 考慮過的替代方案

- **只放 DIB（Phase 2、3 現況）**：可視像素同樣無損，但每個接收端各自轉換 DIB，結果取決於接收端；放入 PNG 後，支援的程式拿到的是與 PNG 檔逐位元組相同的編碼結果。
- **外層重試 5 次、每次 100 ms（原計畫）**：與內建重試相乘，阻塞時間過長。
- **以 P/Invoke 自行開啟剪貼簿並自訂重試**：重複執行階段已有的功能，還要自行管理 `HGLOBAL` 的配置與釋放。
- **WinForms `Clipboard.SetDataObject(data, copy, retryTimes, retryDelay)`**：可以指定重試次數，但會擴大 Windows Forms 的使用範圍（目前只用於系統匣與色彩對話框），而內建重試已經足夠。
- **延遲產生（接收端要求時才編碼 PNG）**：需自行實作 COM `IDataObject`；以 `copy: true` 讓內容在程式結束後保留時，仍須產生全部格式。

## 影響

- PowerPoint 等支援 PNG 的程式改為貼上 PNG 格式，MT-08 必須以新版重新確認。
- 剪貼簿被占用時，內建重試在 UI 執行緒進行，視窗最多約 1～2 秒沒有回應，之後顯示錯誤。占用情境以煙霧腳本實測（另一個處理程序持有剪貼簿），記錄耗時與錯誤碼。
